# Conventions (AI / coding agents)

Concrete rules to follow when modifying this repository, restating and
extending `AGENTS.md` (the repository's own agent guide — read that file
too; this page adds the "where does X belong" decision rules it implies
but doesn't spell out as a table).

## Where does a feature belong?

A new domain area gets its own folder at `src/features/<name>/`, using
whichever of `api/ components/ pages/ schemas/ store/ types/ utils/` it
actually needs. Never add a new top-level directory under `src/` for a
feature — see [Adding a Feature](/development/feature-development).

## Where does API code belong?

- A new WireMock Admin API operation → a method on the relevant existing
  sub-client in `src/shared/api/wiremock-client.ts` (`mappings`, `files`,
  `scenarios`, `requests`, `recordings`, `system`). Do not call Axios or
  `fetch` from anywhere else.
- The hook that calls it → `src/features/<feature>/api/use-*.ts`, using
  `useQuery`/`useMutation`.
- See [Adding an API Operation](/development/api-integration) for the full
  template.

## Where does state belong?

- Anything fetched from WireMock → TanStack Query, never Zustand.
- Anything that must persist across sessions and isn't WireMock data
  (servers, UI prefs, audit log) → a Zustand store with
  `persist(..., { name: 'mockops-<name>' })`.
- Anything ephemeral and local to one component (a search box, a dialog's
  open/closed state) → `useState`, not a store.

Full rationale: [State Management](/architecture/state-management).

## How are routes defined?

One file per route in `src/routes/`, flat and dot-delimited
(`mappings.tsx`, `mappings_.$mappingId.tsx`). A route file only calls
`createFileRoute` and points at a page component — it never contains JSX
beyond that. After adding or renaming a route file, run
`npm run generate-routes` (or `npm run dev`/`npm run build`, which do it
automatically) to regenerate `src/routeTree.gen.ts`.

## How are WireMock operations implemented?

Always through `WireMockClient` (see "Where does API code belong?"
above), and always parsed through a Zod schema from
`src/shared/types/wiremock.ts` on the way out of the sub-client method.
Never trust a raw WireMock JSON response past that boundary.

## How are tests structured?

- Pure logic (matching, parsing, formatting, deriving) → a colocated
  `*.test.ts` next to the function it tests, using `vitest`'s
  `describe`/`it`/`expect`.
- Cross-page flows → `e2e/smoke.spec.ts` (Playwright).
- MockOps does not broadly unit-test components or pages — don't assume
  missing component tests are an oversight to "fix" unprompted; see
  [Testing](/development/testing) for what's actually covered and why.

## Naming and style

- kebab-case filenames (`mapping-editor-page.tsx`, `use-mappings.ts`).
- `use-*.ts` for TanStack Query hook files, one per feature (not one hook
  per file).
- Components are PascalCase exports from kebab-case files.
- Prettier owns formatting; ESLint owns logic/quality
  (`eslint-config-prettier` disables any ESLint formatting rules that
  would conflict) — don't hand-format to work around a Prettier rule.
- Import shared code via the `@/` alias (`@/shared/...`,
  `@/features/...`), not relative paths that climb out of a feature.

## Files that should not normally be modified

- `src/routeTree.gen.ts` — generated, gitignored; regenerate it, don't
  hand-edit it.
- `src/shared/components/ui/*` — vendored/generated ShadCN-style
  primitives. `eslint.config.js` explicitly disables
  `react-refresh/only-export-components` for this directory because these
  files intentionally export variant helpers alongside components — don't
  "fix" that lint exception, and prefer composing these primitives over
  editing them.
- `docs/public/llms-full.txt` — generated by
  `docs/.vitepress/generate-llms-full.mjs` on every `docs:build`;
  gitignored. Edit the source pages instead.

## Architectural boundaries to preserve

- **No backend.** Don't introduce a server-side process, API route, or
  database — see
  [Architecture Decisions: Static SPA](/reference/architecture-decisions#static-spa-with-no-backend).
- **No bypassing `WireMockClient`.** Every WireMock call goes through it.
- **No mixing TanStack Query and Zustand roles.** WireMock data never
  lives in a Zustand store; MockOps' own config/prefs never live in
  TanStack Query.
- **Keep `.catchall(z.unknown())`** on every WireMock-facing Zod schema.
- **Query keys always include `server?.id`.** This is what makes
  multi-server switching work without manual cache management.
- **Every mutation logs to the audit store on success** — see the
  mutation hook template in [Architecture Reference](/ai/architecture).

## Commit / branch conventions

From `AGENTS.md`: branches are named `feature/<desc>`, `fix/<desc>`, or
`chore/<desc>` (lowercase, hyphen-separated) — never after the agent or
session. Don't open a pull request or push to `main` unless explicitly
asked.
